Задача 3 — 409 при удалении + сломанная сортировка «Сначала новые» — 2026-11-22

Агент: ZCode (GLM)

Запрос пользователя

  1. Пытаюсь удалить карточку - GitHub API: HTTP 409
  2. Самые новые карточки должны быть СВЕРХУ, т.к. стоит Сначала новые, а он наоборот их вниз отправил. Исправляй.

Что сделано

  • 409: причина — GET содержимого GitHub API кэшировался браузером (до минуты), PUT шёл со старым sha. В js/api.js: cache: 'no-store' для всех запросов + putWithRecovery (перечитывание файла при 409: noop при совпадении контента, диалог конфликта если менял кто-то другой, повтор со свежим sha; для overwrite — всегда повтор). Проблема у пользователя уже разрешилась повторами (живой db.js содержит его удаление), теперь — автоматически.
  • Сортировка: добавленные при импорте addedAt были в RFC-формате пинов («Wed, 26 Aug 2026…»), а сайт пишет ISO — строковое сравнение смешивало форматы и отправляло ISO-даты вниз. Компаратор теперь через Date.parse; все 33 старых addedAt мигрированы в ISO; в tools/import-pinterest.mjs добавлен isoDate.
  • Masonry: CSS columns наполняет колонку сверху вниз — «новые» визуально уезжали вбок. Переведено на round-robin колонки (renderGallery + .m-col flex), чтение слева направо как в Pinterest, пересчёт колонок на resize. Проверено: верхний ряд = 5 самых новых (topRowCorrect:true).
  • Бонус: «Брат 2» (новейшая карточка пользователя) — перезаполнено описание/постер/год (поиск попал в статью «URL»).

Изменённые файлы

  • js/api.js — no-store, putWithRecovery
  • js/app.js — компаратор Date.parse, masonry round-robin, resize-пересборка (?v=3)
  • css/style.css — flex-сетка вместо CSS columns (?v=2)
  • tools/import-pinterest.mjs — isoDate для addedAt
  • data/db.js — addedAt → ISO, исправлен «Брат 2»

Как проверить

  • На живом сайте после push + F5: «Сначала новые» — верхний ряд слева направо = самые свежие; удаление карточки проходит без 409 (при гонке автоматически).
  • Локально: dev-сервер → удаление карточки → data/db.js меняется.

Решения и допущения

  • 409 обработан авто-восстановлением, а не показом ошибки: перечитывание различает «уже наш контент» (noop), «чужой коммит» (диалог конфликта) и «просто устаревший sha» (повтор).
  • Для overwrite 409 всегда повторяется с свежим sha — пользователь уже принял решение перезаписать.

Открытые вопросы и риски

  • Живой 409-сценарий проверен только ревизией кода (токены не трогаем); механизм перечитывания покрывает известные причины 409 Contents API.
